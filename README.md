### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в своих домах.
- Пользователи могут просматривать статус отопительных приборов (вкл/выкл) в своих домах.
- Пользователи могут изменять температуру на отопительных приборах.
- Система поддерживает удаленное управление отоплением.

**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс.
- Система получает данные о температуре с датчиков, установленных в домах.

### 2. Анализ архитектуры монолитного приложения

**Язык программирования:** Go  
Необычный выбор языка для имеющегося монолита, с одной стороны, он позволяет писать быстрый код. Но с другой стороны, приложение гораздо раньше упрется в ограничения архитектуры.
Также, Go-специалистов на рынке сложнее найти, чем специалистов по Java или Python. Поэтому для написания будущего микросервисного решения я бы предложил 
использовать более мейнстримные языки. Возможно, оставить Go для самых критических по производительности частей, если будет такая необходимость.

**База данных:** PostgreSQL  
Хорошая производительная СУБД. Ее и оставим

**Архитектура:** Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.  
Недостатки монолита в нашей конкретной ситуации описаны ниже в разделе "Проблемы монолитного решения".  

**Взаимодействие:** Синхронное, запросы обрабатываются последовательно.  
Синхронное взаимодействие оправдано в ряде случаев, например, для CRUD-операций, не выходящих за границы нашей системы и не завязанных на какие-то
длительные ожидания ответа. Но местами можно улучшить пользовательский опыт, а также снизить риски падения производительности системы, добавив 
асинхронности. Например, при обновлении показаний устройств.

**Масштабируемость:** Ограничена, так как монолит сложно масштабировать по частям.  
Возможно по сути только вертикальное масштабирование за счет наращивания железа. Но это достаточно серьезное ограничение по мере роста клиентской базы.
Текущая кодовая база не позволяет горизонтально масштабировать монолит из-за отсутствия синхронизации и, как следствие, риска возникновения гонок при 
одновременном доступе к системе. 

**Развертывание:** Осуществляется с помощью docker-compose. Требует остановки всего приложения.
В целом, неплохое решение для монолита, поскольку контейнеров не так много. В идеале при дальнейшем развитии и переходе на микросервисную архитектуру стоит
посмотреть в сторону Kubernetes, что позволит автоматизировать ряд операций (масштабирование, перезапуск и распределение контейнеров по подам и т.д.)

### 3. Определение доменов и границы контекстов

- Домен "Управление устройствами" 
  - все, что относится к управлению датчиками: их добавление в систему, изменение состояния, удаление
  - сюда входят ендпоинты `POST /sensors`, `PUT /sensors/:id`, `DELETE /sensors/:id`, `PATCH /sensors/:id/value`
- Домен "Мониторинг температуры"
  - получение температуры по датчику или локации
  - сюда входят ендпоинты `GET /sensors`, `GET /sensors/:id`, `GET /sensors/temperature/:location`
- Домен "Интеграция с вендорами" 
  - интеграция с 3rd-party системой, которая возвращает показания температуры
  - представлен [temperature_service.go](/apps/smart_home/services/temperature_service.go)
- Домен "Мониторинг состояния системы" 
  - телеметрия монолита
  - представлен ендпоинтом `GET /health`

### **4. Проблемы монолитного решения**

- Пользователи не могут самостоятельно подключать новые устройства.
- Пользователи не могут самостоятельно создавать новые локации, а также перемещать устройства из одной локации в другую.
- Подключение нового устройства требует личного присутствия специалиста на объекте.
- При росте пользовательской базы масштабировать монолит может быть сложно.
- Текущая схема с синхронными запросами обладает низкой надежностью: если по какой-то причине, скажем, запросы в БД начнут зависать, то исчерпается 
пул соединений и все пользователи потеряют возможность пользоваться приложением до устранения проблем.
- Добавление новых типов и конкретных моделей устройств (освещение, автоматика ворот и т.п.) потребует изменения кодовой базы.
- Текущее решение не предполагает никакого разделения доступа к датчикам, что неизбежно вызовет проблемы с безопасностью.
- Совместная работа над проектом затруднена из-за общей кодовой базы и сильной связности кода.

# Задание 4. Создание и документирование API

### 1. Тип API

Взаимодействие между нашими микросервисами будет осуществляться по REST API, поскольку большая часть операций у нас синхронна (например, весь CRUD).
Для взаимодействия с внешними устройствами будем использовать асинхронный подход с использованием Kafka. Это позволит не занимать ресурсы, ожидая 
синхронных ответов, которые могут задерживаться из-за плохого интернета, проблем на стороне вендора или еще каких-то причин.

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры

Ревьюер будет проверять точно так же.
